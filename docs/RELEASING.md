# Releasing

A release is created by pushing a version tag. The **Release** workflow (`.github/workflows/release.yml`) does the rest: it builds the Windows, macOS and Linux installers, attaches them to a GitHub release with generated notes, and publishes it.

## Cutting a release

1. **Start from a green `main`.**

   ```sh
   git checkout main
   git pull
   ```

   Check that the latest CI run on `main` passed.

2. **Bump the version.** One command updates `package.json`, `package-lock.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock` and `src-tauri/tauri.conf.json` together:

   ```sh
   npm run version:bump -- patch     # 0.1.0 -> 0.1.1  bug fixes
   npm run version:bump -- minor     # 0.1.0 -> 0.2.0  new features
   npm run version:bump -- major     # 0.1.0 -> 1.0.0  breaking changes
   npm run version:bump -- 1.4.0     # or set an exact version
   ```

   Run it with no argument to see the current version in each file.

3. **Commit and tag.** The tag must be `v` plus the exact version, or the workflow stops at its first step.

   ```sh
   git diff                                   # five files, version lines only
   git commit -am "chore: release v0.2.0"
   git tag v0.2.0
   git push origin main v0.2.0
   ```

   If `main` is protected, push the version commit through a pull request, merge it, then tag the merge commit and push the tag.

4. **Watch the run** under the repository's Actions tab. A full release takes roughly 15 to 25 minutes, mostly the first Rust compile on each platform.

5. **Check the published release.** It appears at `https://github.com/theonlytruebigmac/n-voke/releases` with the installers attached. Edit the generated notes if you want to add context.

## What the workflow does

| Job | Purpose |
|---|---|
| **Verify** | Fails unless the tag equals `v<app version>` in all five files. Then runs the frontend build, frontend tests and Rust tests, so a tag on a broken commit never ships. |
| **Draft release** | Creates a draft release for the tag with notes generated from merged pull requests, or reuses the draft if one exists. Tags containing a hyphen are marked as pre-releases. |
| **Build** | Runs once each on Windows, macOS and Linux and uploads the installers to the draft. |
| **Publish release** | Runs only if every build succeeded. Flips the draft to public and marks it Latest (stable releases only). |

Because the release stays a draft until the last job, a failed build never leaves a half-populated public release.

Installers produced:

| Platform | Files |
|---|---|
| Windows | `.msi` and `.exe` (NSIS) |
| macOS | universal `.dmg` for Apple Silicon and Intel |
| Linux | `.AppImage`, `.deb`, `.rpm` |

## Pre-releases

Use a numeric pre-release suffix, for example:

```sh
npm run version:bump -- 0.3.0-1
git commit -am "chore: release v0.3.0-1"
git tag v0.3.0-1 && git push origin main v0.3.0-1
```

The workflow publishes it marked **Pre-release** and does not make it Latest. The suffix has to be numeric because the Windows MSI format rejects `-beta.1` style identifiers. The version script warns if you use one.

## When something goes wrong

**A build job fails.** The release stays a draft and nothing public changes. Fix the cause, then either re-run the failed jobs from the Actions run page, or push a fix and re-tag (below).

**Re-running for an existing tag.** In Actions, choose **Release**, then **Run workflow**, and under "Use workflow from" pick the tag. The existing draft or release is reused and its installers are replaced.

**The tag points at the wrong commit, or the version was wrong.** Delete the draft release in the GitHub UI, delete the tag, fix the problem, and tag again:

```sh
git push --delete origin v0.2.0
git tag -d v0.2.0
# fix, commit, push, then
git tag v0.2.0
git push origin v0.2.0
```

Avoid doing this after a release is public; users may already have downloaded it. Ship a new patch version instead.

**"tag does not match the app version".** The version files and the tag disagree. Run `npm run version:check` to see which file is off, and `npm run version:bump -- <version>` to resync.

**The release job can't create a release or upload files.** Check that the repository allows the workflow to write: Settings, Actions, General, Workflow permissions. The workflow declares the permissions it needs (`contents: write` on the jobs that publish), but an organization policy can still cap them.

## Release notes

Notes are generated by GitHub from pull requests merged since the previous release and grouped by label (`.github/release.yml`):

| Label | Section |
|---|---|
| `enhancement`, `feature` | New features |
| `bug`, `fix` | Fixes |
| `documentation` | Documentation |
| anything else | Other changes |
| `ignore-for-release` | Left out |

Label pull requests before merging them and the notes need little editing.

## Unsigned builds

The installers are not code-signed, so macOS Gatekeeper and Windows SmartScreen warn on first launch. Users can open the app anyway (macOS: right-click, Open; Windows: More info, Run anyway).

Signing is not configured. Adding it means an Apple Developer ID certificate and notarization credentials, and a Windows code-signing certificate, stored as repository secrets and passed to `tauri-apps/tauri-action` in the **Build** job's `env`. Tauri's [signing guides](https://tauri.app/distribute/sign/macos/) list the exact variables.

## Version script reference

`scripts/version.mjs` has no dependencies and can be run directly with `node` or through the npm scripts.

| Command | Result |
|---|---|
| `npm run version:bump` | Print the version in each file |
| `npm run version:bump -- patch\|minor\|major` | Increment and write to all files |
| `npm run version:bump -- 1.2.3` | Set an exact version (a leading `v` is accepted) |
| `npm run version:check` | Exit non-zero if the files disagree |
| `node scripts/version.mjs --check --tag v1.2.3` | Also require the tag to match; this is what the workflow runs |

The script edits only the version lines, so diffs stay minimal.
